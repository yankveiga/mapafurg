1) RESUMO EM 1 MINUTO
========================================================================
Este projeto tem duas partes principais:

1. Frontend (React + Leaflet):
   - mostra o mapa do campus;
   - permite buscar predios;
   - abre painel com detalhes;
   - recebe a localizacao do onibus em tempo real por WebSocket.

2. Backend (Node + ws):
   - recebe coordenadas enviadas por apps rastreadores externos;
   - valida formato e token;
   - guarda a ultima posicao de cada onibus em memoria;
   - envia atualizacoes para todos os clientes conectados no mapa.

Observacao sobre o rastreador:
- este repositorio nao inclui o app do celular/dispositivo rastreador;
- para o onibus aparecer em tempo real, um app externo precisa obter o GPS e
  enviar mensagens bus_location para o servidor WebSocket.

Decisao de arquitetura:
- mapa no Vercel (site estatico);
- WebSocket em servidor separado (Render, laboratorio, etc.).
Motivo: Vercel nao e usado como servidor WS persistente nesse fluxo.

========================================================================
2) FLUXO TECNICO COMPLETO (DO CELULAR ATE O MAPA)
========================================================================
Passo 1: app rastreador externo envia JSON para o WS
Exemplo:
{
  "type": "bus_location",
  "token": "SEU_TOKEN",
  "lat": -32.07,
  "lng": -52.16,
  "timestamp": "2026-04-21T12:00:00.000Z"
}

Passo 2: server/ws-server.js recebe a mensagem
- verifica type, token, lat/lng validos;
- normaliza os campos;
- define busId:
  - se o app enviou busId valido, preserva esse identificador;
  - se nao enviou, usa id automatico/generico conforme configuracao.

Passo 3: servidor faz broadcast
- envia o payload para todos os sockets conectados.

Passo 4: src/hooks/useBusLocations.js recebe no navegador
- ws.onmessage faz parse JSON;
- se for bus_location valido, atualiza estado onibusPorId;
- React renderiza/atualiza o marcador no Leaflet;
- o marcador usa a coordenada recebida como posicao real e interpola apenas
  a representacao visual no frontend.

Passo 5: interface mostra status
- "Ao vivo", "Offline", "Erro";
- quantidade de onibus ativos;
- "ultima atualizacao ha Xs";
- opacidade do marcador conforme a idade da ultima posicao real recebida.

3.3 src/App.jsx (orquestrador da interface)
-----------------------------------------------------------------------
Papel:
- orquestra a tela principal do mapa.
- combina busca, dados estaticos, status dos onibus e componentes visuais.
- a logica mais especifica foi separada em modulos menores.

Blocos principais:

A) Estado React principal
- busca: texto do input.
- solicitarGps: contador-gatilho para centralizar no usuario.
- solicitarOnibus: contador-gatilho para centralizar no onibus.
- predioAberto: item do drawer inferior.
- menuAberto: menu lateral.
- agoraMs: relogio para atualizar "ultima atualizacao".

B) Conexao WebSocket
- App.jsx monta wsUrl.
- useBusLocations(wsUrl) devolve:
  - onibusPorId;
  - statusWs.

C) Busca de predios
- traduzirBusca(busca) retorna:
  - idsExtras (atalhos/aliases curados)
  - termosBusca (texto normalizado)
- filtro final usa:
  - id, nome, aliases e projetos.

D) Render da interface
- menu lateral com atalhos.
- barra superior com busca.
- botoes flutuantes (GPS usuario e centralizar onibus).
- badge com status do onibus.
- drawer inferior via PredioDrawer.
- MapContainer com tiles OSM.
- MarkerClusterGroup para predios.
- marcador de onibus:
  - sem onibus conhecido -> mostra fallback em POSICAO_INICIAL_ONIBUS;
  - com onibus conhecido -> mostra marcadores dos onibus em tempo real ou a
    ultima posicao real preservada;
  - calcula opacidade do marcador com calcularOpacidadeOnibus(timestamp, agoraMs).

Observacao importante:
- no estado atual, maxBounds esta comentado.
- portanto, nao ha bloqueio geografico rigido da navegacao.

3.4 src/utils/buscas.js
-----------------------------------------------------------------------
Papel:
- motor semantico da busca.

O que faz:
1) normaliza texto (minusculas, sem acento, sem simbolos).
2) normaliza consulta compacta (remove termos tipo "predio", "sala").
3) traduz apelidos para ids (objeto rotas).
4) aplica busca parcial por chave para nao "sumir resultado" digitando.
5) trata regras especiais:
   - prefixos (ex.: eg123 -> expressao_grafica)
   - pavilhao explicito
   - numero de sala (ex.: 4103 -> pavilhao_4)

Saida:
- idsExtras: ids forcados.
- termosBusca: termo para filtro textual complementar no App.jsx.

Por que foi feito assim:
- separa regra de negocio da busca do arquivo de interface.

3.9 src/services/busTracking.js
-----------------------------------------------------------------------
Papel:
- validar e preparar cada atualizacao antes de alterar o marcador.

Regras iniciais:
- descarta timestamp antigo ou repetido;
- ignora accuracy acima de 40 metros;
- ignora salto com velocidade calculada acima de 30 m/s;
- desconsidera deslocamento inferior a 2 metros;
- calcula duracao de interpolacao entre 900 e 2200 ms;
- calcula opacidade pela idade da ultima posicao real.

Interpolacao:
- acontece somente no frontend;
- nao altera o protocolo WebSocket;
- nao envia posicoes interpoladas ao servidor;
- nao aumenta a frequencia do rastreador;
- usa o intervalo entre timestamps recebidos como base.

Referencia atual:
- o estimador de consumo e o README usam intervalo de envio de 3 segundos;
- por isso a animacao fica limitada a 2200 ms, deixando margem antes da
  proxima atualizacao esperada.

Opacidade:
- ate 10 segundos sem nova posicao real: 100%;
- de 10 a 30 segundos: reducao gradual ate cerca de 70%;
- de 30 a 60 segundos: reducao gradual ate cerca de 30%;
- acima de 60 segundos, ou sem timestamp valido: cerca de 30%.

Os valores ficam em BUS_TRACKING_CONFIG e devem ser calibrados em campo.

3.11 server/ws-server.js (backend tempo real)
-----------------------------------------------------------------------
Papel:
- servidor HTTP + WebSocket.

Config de ambiente:
- PORT / WS_PORT
- WS_HOST
- BUS_ID
- WS_AUTH_TOKEN
- BUS_ID_PREFIX
- AUTO_ASSIGN_BUS_ID

Responsabilidades:
1) endpoint /health:
   retorna ok, conexoes ativas e onibus ativos.
2) handshake WS:
   aloca slot bus-1, bus-2, ... quando autoassign ligado.
3) validacao:
   type=bus_location, token valido (se configurado), lat/lng validos.
4) normalizacao:
   padroniza payload com timestamp e serverReceivedAt.
   Se o app enviar busId valido, esse busId e preservado.
   Se nao enviar, o servidor usa o id automatico/generico.
5) broadcast:
   envia para todos os clientes conectados.
6) close:
   remove onibus desconectado e emite bus_disconnected.

Observacao:
- o servidor emite bus_disconnected ao fechar a conexao do rastreador;
- no frontend, essa mensagem nao remove imediatamente o marcador do mapa.
  A ultima posicao real conhecida permanece visivel e fica mais transparente
  conforme envelhece.

Por que foi feito assim:
- arquitetura simples, sem dependencia de banco.
- baixa latencia para exibicao em tempo real.

Limitacao conhecida:
- estado em memoria (nao persiste apos restart).

Observacao sobre o app rastreador:
- o servidor nao depende de uma pasta do rastreador dentro deste repositorio;
- qualquer app ou dispositivo pode ser usado como rastreador, desde que envie
  o JSON bus_location no formato aceito pelo server/ws-server.js;
- se WS_AUTH_TOKEN estiver configurado no servidor, o app rastreador tambem
  precisa enviar o mesmo token no payload.
- o campo busId e opcional:
  - apps novos podem enviar onibus_amarelo, onibus_branco ou onibus_teste;
  - apps antigos sem busId continuam funcionando com ids automaticos.

========================================================================
4) POR QUE CADA DECISAO TECNICA FOI TOMADA
========================================================================
1. WebSocket separado do front:
   - simplifica deploy do mapa no Vercel;
   - permite hospedar realtime em qualquer servidor.

2. Estado em memoria no WS:
   - suficiente para prototipo/operacao leve;
   - reduz complexidade inicial.

3. Base estatica (src/data/predios.js):
   - facilita manutencao por estudantes sem infra de banco.

4. Busca semantica em modulo separado:
   - reduz acoplamento com interface;
   - facilita evoluir regras de busca.

5. Reconexao automatica no front:
   - melhora resiliencia em redes instaveis.

5) ONDE ALTERAR CADA COISA RAPIDAMENTE
========================================================================
- URL do WS no front: variavel VITE_WS_URL (ambiente Vercel)
- URL do WS local fallback: src/App.jsx (montagem wsUrl)
- token no servidor: WS_AUTH_TOKEN
- URL/token no rastreador: configuracao do app rastreador externo
- formato de validacao do payload: server/ws-server.js (validarMensagemLocalizacao)
- cadastro de onibus: src/data/onibus.js (ONIBUS_CONFIG)
- visual do icone do onibus: src/utils/mapIcons.js (criarIconeOnibusAoVivo)
- arquivo SVG usado por cada onibus: src/data/onibus.js (campo icone)
- posicao padrao do onibus offline: src/data/onibus.js (POSICAO_INICIAL_ONIBUS)
- conexao WS no frontend: src/hooks/useBusLocations.js
- painel inferior de predio: src/components/ui/PredioDrawer.jsx
- dados dos predios/horarios/cardapio: src/data/predios.js
- regras de busca: src/utils/buscas.js

========================================================================
6) RISCOS E LIMITACOES
========================================================================
1. Sem persistencia:
   - restart do WS limpa ultimo estado dos onibus.
2. Sem historico:
   - sistema mostra estado atual, nao trilha historica salva.
3. Dependencia de qualidade de GPS e rede no celular:
   - pode haver salto de posicao.
4. Seguranca baseada em token:
   - precisa manter token fora do Git.
